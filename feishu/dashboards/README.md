## ⚠ 为什么必须入库

**本地没有任何脚本能重建这些卡片。**

- `src/feishu_setup.py` 只建**表结构**（字段），不写卡片；
- `src/sync_runs.py` 是读 `runs/` 往表里推**记录**，也不碰卡片；
- 卡片是在飞书界面上逐条配出来的，官方 OpenAPI 也没有 per-card 读写接口。

放在 `feishu/dashboards/` 之前它们躺在 `.scratch/`（已被 `.gitignore` 忽略）——一次误删就只剩飞书里那一份。
2026-09-13 按常硕要求移到这里入库。

## 口径：以线上为准，改线上要同轮抄回

**这份快照不是生成源，是镜像。** 因此：

- **飞书界面是权威**。改了线上卡片（标题 / 轴字段 / 筛选 / 数字），要**同一轮**把改后的配置抄回这里的 JSON，
  否则本地和线上又会出现两份口径；
- 早期的"唯一本地副本"说法已作废——那时把它当生成源，但界面改得比本地快，本地反而成了过期的那份；
- 改之前建议先照 `qa04_boundary` 的样子把**实测**结果写进来（能读到的字段才写，读到什么写什么）。

## 格式

每个文件是一个对象，`text` 字段是卡片正文（Markdown 语法，飞书卡片支持粗体）；指标类卡片另外带数字字段。示例：

```json
{"text":"**EvalKit 评测驾驶舱** —— 一句话：把 LLM 评测的判定结论做成可交代的数字与归因。…"}
```

图表 / 指标卡的字段：

| 键 | 含义 |
|---|---|
| `table_name` | 数据源表名 |
| `count_all` | 计条数（指标卡的"计数"口径） |
| `series[]` | 数值字段 + `rollup`（`AVERAGE` 等） |
| `group_by[]` | 类别轴字段 + `mode`（`integrated` = 勾选「汇总相同的类别」），可带 `sort` |
| `filter` | `conjunction` + `conditions[]` |
| `number_format` | 小数位（如 `{"formatName":"digital","precision":1}`） |

**取值词表**（照飞书界面原文转写）：

- `conjunction`：`and` = 符合以下**所有**条件；`or` = 符合以下**任一**条件
- `operator`：`is` = **等于**；`isNot` = **不等于**
- `group_by[].sort`：`{"type":"value"|"record","order":"asc"|"desc"}` = 排序依据 纵轴值/记录顺序 × 正序/倒序

## 2026-09-15 全量筛选审计（读「case判定明细」的卡片）

**背景**：QA 两张卡的标题都带「（闭卷）」，筛选却是空的——聚合了全部 60 行（开卷 30 + 闭卷 30）。
"标题声称的口径 ≠ 实际筛选口径"是一类问题，不是两张卡的偶发失误，所以把三张仪表盘里所有读同一张
`case判定明细` 表的卡片都过了一遍。

**做法**：脚本逐卡打开配置面板，只读两样东西——① 面板标题输入框的值（卡片身份的**唯一**可靠来源，
`title-child` 在隐藏副本里会取错）；② `数据范围` 那行的 `筛选 (n)` 条数 + 弹层里的实际条件。

**结论**：5 张卡中 3 张正确、2 张为空。空的 2 张已补 `run_id = 20260909-173030` 且 `结论 = 失败`，
重开面板复核显示 `筛选 (2)`，与 `qa05_catfail.json` / `qa06_faillist.json` 的快照一致。
驾驶舱 3 张同类卡（失败归因 / 失败类型 / 失败 case 清单）本来就是对的。

**踩坑（以后改卡片筛选必读）**：

- 筛选弹层**没有确定按钮**，点弹层外部即提交——但"外部"必须落在**配置面板内部**；
- 点到仪表盘卡片上会让编辑器**切换卡片**，等于放弃这次编辑（实测两次都这样丢的，面板重开后条数仍为 0）；
- 正确收尾：填完先点面板标题输入框（面板内空白）提交，再关面板。

**遗留观察（数据正确但呈现单薄，记录不改）**：`qa05_catfail` 在闭卷下只有 `normal 7` 一根柱子——
闭卷 7 个失败 case（C001/C002/C006/C010/C012/C013/C015）的 `category` 全是 `normal`。
若要更有信息量，可考虑改按**失败类型**分组（那 7 条全落在「否决-事实」）。
