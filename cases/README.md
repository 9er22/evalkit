## 写 case 的三条要求

- **输入要能直接复制**。写成完整的 prompt，不要写"问一个关于 X 的问题"。
- **期望要可观察**。写"回答里必须出现 Y"，不要写"回答得准确"。
- **每个 case 说清它测的是哪一类失败**。否则 rubric 设计阶段你会发现没法归类。

## 额外的第四栏：语料依据

模板之外，每个 case 多了一栏 **「语料依据」**——答案在 `research/corpus/CORPUS.md` 里的哪个确切字符串。

加这一栏的原因：rubric 里有「标准版本可追溯」这一维，**case 自己得先可追溯**。有了它，任何人用一条 grep 就能验证"这个答案到底在不在语料里"，不用靠记忆或感觉。

- normal / 部分 edge：给出语料中确切存在的字符串
- 用来检验"会不会编造"的 case：明确标「（语料中不存在）」

生成后已全量校验：22 条依据 100% 命中语料；反向核对 `min_length`、`status_code`、`ge=1`、`UploadFile`、`response_model_exclude_password`，确认在语料中出现 0 次。

## 这 30 个 case 的分布思路

- **normal（18）**：路径参数、查询参数、请求体、响应模型四大块各 4—5 题，覆盖文档里可查证的核心事实。优先挑**容易被记错**的点（比如 bool 转换接受的 5 种写法、`{file_path:path}` 这个特殊语法）。
- **edge（7）**：分两种。
  - **语料完全没覆盖**（查询参数长度校验、数值范围、状态码、文件上传）—— 测会不会编。
  - **语料只提了一句、或立场微妙**（不用 Pydantic 怎么声明 body、include/exclude 推不推荐、返回数据库对象怎么办）—— 测能不能分清"提到过"和"讲过"。
- **adversarial（5）**：提示注入（C026）、诱导编造一个名字很像真参数的假 API（C027）、权威压力下会不会改口（C028）、无意义的越界索取（C029）、错误前提会不会被附和（C030）。
