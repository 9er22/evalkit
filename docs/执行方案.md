# 两周执行方案

## 为什么是这个题目

1. **场景会替你说话**。作品集里放冷门场景，会反向限制机会。
2. **但经验没白费，只是位置放错了**。"规则不一致、临时改标准导致返工"的本质就是**质量评估**——这正是当前 AI 领域公认的最大短板。
3. **Eval 是结构性需求，不是风口**。只要模型输出有不确定性就需要评估，它不会像某个具体行业那样过时。

## 热点证据（GitHub，2026 年多个生态清单交叉一致）

- Agent / 多智能体编排是主流：LangGraph、CrewAI、OpenAI Agents SDK、Google ADK
- MCP 成为连接工具与数据的标准
- **Observability and evals 被明确写作 "table stakes for production agents"**
- 三个最热落地形态：Deep Research Agent、Browser/Computer Use、Coding Agent
- 国内代表：字节 DeerFlow（Deep Research，25k+ stars，2026 年 2 月 GitHub Trending 第一）

**所有人都在做 Agent，几乎没人做 Eval** —— 差异化在这里。而且 eval 设计是面试中最能立刻建立可信度、也是最多人没准备的一件东西。

## 题目定义

- 输入：一批测试 case + 被测应用
- 输出：通过率、失败分类、版本间回归对比
- 核心不是代码多复杂，是**评分标准（rubric）设计得对不对**

**首个被测对象**：见 `research/被测对象候选.md`

## 节点 1｜9/9—9/11：定被测对象 + 设计 case

- 选定被测的 AI 应用
- 设计 **30 个 case**：18 正常 / 7 边界 / 5 对抗（提示注入、诱导、越界）
- 每个 case 写清：输入、期望、你怎么判断它过没过

**产出**：`cases/` 30 个 case + `research/被测对象说明.md`

## 节点 2｜9/12—9/15：设计评分标准（rubric）

整个作品最值钱的部分：

- 每个 case 从哪几个维度打分（如：事实性、有用性、格式遵循、拒绝是否恰当）
- 每个维度的评分档位（1—3 分，每档要有具体描述，不能只写"好/一般/差"）
- 用 AI 生成第一版 rubric，**你来改**，留下修改痕迹

**产出**：`rubrics/` 评分标准 + 一页"我改了什么、为什么"

## 节点 3｜9/16—9/19：跑起来 + 出界面

- 写一个脚本批量跑 30 个 case（LLM-as-judge，AI 帮你写）
- 用 Gradio 或 Streamlit 出界面：上传 case → 跑 → 看报告
- 优先跑通，不要追求工程完备

**产出**：可运行脚本 + 一个能打开的界面

## 节点 4｜9/20—9/22：分析报告 + 交叉验证

1. 评测报告：整体通过率、按维度分布、失败分类（最典型的 5 个失败）
2. **把 rubric 和报告丢给别的 Agent** 挑毛病，记录它提了什么、你认不认同
3. 一页结论：这个应用现在最该改什么，为什么

**产出**：`reports/` 评测报告 + 一页交叉验证记录
