# Domain Docs

工程类技能在探索本仓库时，应如何消费领域文档。

## 探索之前，先读这些

- **`CONTEXT.md`**（仓库根目录）——目前**不存在**，读到就跳过。不要提示、不要主动建议创建
- **`docs/决策记录.md`**——本仓库的 ADR 日志，决策编号为 `D1`、`D2`……涉及你要改动的区域时必读
- **`docs/执行方案.md`**——两周冲刺的节点计划与失败判定。动手前先确认当前处在哪个节点

**本仓库没有 `docs/adr/` 目录**，决策统一记在 `docs/决策记录.md` 一个文件里。**不要新建 `docs/adr/`**——那会造成两套决策记录。

ADR 编号格式是 `D<n>`（例如 D5）。引用时写"决策记录 D5"，**不要**编造 `ADR-0007` 这类编号。

## 文件结构

single-context（本仓库不是 monorepo）：

```
/
├── CONTEXT.md              ← 尚不存在
├── docs/
│   ├── 决策记录.md          ← ADR 日志（D1…）
│   ├── 执行方案.md          ← 节点计划与失败判定
│   └── agents/             ← 本目录，agent 配置
├── cases/                  ← 测试 case（30 个：18 正常 / 7 边界 / 5 对抗）
├── rubrics/                ← 评分标准，项目最值钱的部分
├── research/               ← 背景调研与一手素材
├── runs/                   ← 每次跑评测的原始结果
├── reports/                ← 评测报告与结论
└── src/                    ← 评测脚本
```

## 使用术语表里的词汇

输出中提到领域概念时（issue 标题、重构提议、假设、测试名），用 `CONTEXT.md` 里定义的说法，不要漂移成术语表明确回避的同义词。

`CONTEXT.md` 现在还没有，所以**以本仓库已有的公开词汇为准**：

`case`、`rubric`、`run`、`report`、`维度`、`档位`、`门槛`、`节点`、`被测对象`、`语料`、`失败分类`、`版本间回归对比`、`标准版本可追溯`。

含义见 `README.md` 以及 `cases/README.md`、`rubrics/README.md`。

如果需要的概念不在里面，那是信号：要么你在发明项目不用的语言（重新考虑），要么确实有缺口（记下来交给 `/domain-modeling`）。

## 标记 ADR 冲突

如果输出与既有决策矛盾，要显式指出，不要静默覆盖：

> _与决策记录 D5（亲历的用途边界）矛盾，但值得重开，因为……_
