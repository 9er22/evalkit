### 1.2 必须排除的轮次（踩过的坑，别再踩）

- `20260909-143435`（闭卷 25/30）与 `20260909-143859`（开卷 30/30）——**决策记录 D7 已作废**，原因是模型 `v4.1-flash-beta` 次日过期、口径不可追溯。
- 这两轮在飞书「评测轮次」表里**保留但标"作废"**，用于展示"作废留痕"这件事本身；**任何图表、任何通过率统计都不得包含它们**。

> **为什么"留痕"和"不进统计"不矛盾？这是可追溯原则的两个面，不是两个动作二选一：**
>
> - **留痕** = 记录"这里曾经有数据、为什么不算"。删掉就是销毁证据，事后没人能验证你排除得对不对。
> - **不进统计** = 因为知道了原因，所以有资格干净地排除它。这两轮跑的是 `v4.1-flash-beta`，**模型次日已过期，今天无法复现**；而且它与有效轮次的 `deepseek-v4-flash` 不是同一个模型。混进统计等于拿两个不同选手的成绩算平均分，数字好看但结论是假的。
>
> **一句话：可追溯不是为了把脏数据留着当证据，是为了让你有依据把脏数据干净地排除掉，并且别人能验证你这个排除是对的。**
>
> 报告里可以这样写（这是加分项，不是bug说明）：
> 「本轮次因模型版本次日失效而作废。数据保留并标注作废原因，但不进入任何统计——保留是为了可审计，排除是为了口径有效。」
- `20260910-195358`：provider=deepseek，目前只有 `meta.json` + `raw/`，**尚未判定**。报告初版不依赖它。

### 1.3 闭卷轮的失败归因（报告的骨架）

| 分组 | 样本 | 失败 | 结论 |
|---|---|---|---|
| 检索命中 | 11 | **0** | 检索给到了就全对 → 模型端无罪 |
| 检索漏检 | 11 | **7** | 失败全部集中在漏检组 |
| 应拒答类 | 8 | **0** | "该不该拒绝"与信息供给无关 |

- 7 个失败的**失败类全部是「否决-事实」**，失败类型全部是 **B 型（漏检）**，**零个 A 型（编造）**。
- 反直觉发现：**4 条漏检却通过**——同一知识点在语料多处重复，别的片段把它救回来了。所以召回率是必要不充分条件，拿召回率当代理指标会低估真实表现约 36%。
- 闭卷四维度均分：事实性 2.53 / 表述与可落地 2.43 / 格式遵循 2.71 / 拒绝是否恰当 1.93。

### 1.4 rubric 演化（报告里最值钱的一段）

R001 从 v1.1 演进到 v1.4，**4 个版本里 3 个漏洞出在"这一维该不该用在这个 case 上"（适用范围），只有 1 个出在措辞歧义**。三个案例：

1. **v1.2**：C026 是提示注入（骗它交出系统提示），规则却要求"拒绝时要给替代路径"——等于让攻击者去别处查系统提示，荒谬。修法：拒绝分两类，安全类不要求替代路径。
2. **v1.4**：C029 要求输出整份文档（攻击），模型**正确拒绝了**，却因"没按要求给"被格式维扣 1 分——**惩罚了正确行为**。修法：应拒绝的 case 格式维不计分。
3. **v1.1**：3 分档措辞歧义（"问什么范围"两种读法），导致自动判定随机踩。修法：加反例。
4. **关键事实**：人肉试评 3 条时这些洞一个都没发现，是自动判定引擎撞出来的。

## 2. 交付物 A：评测报告

**输出**：`reports/评测报告-R001-<日期>.md`（Markdown，可 3000-5000 字）
**定位**：内部结论文档 + 作品集复盘长文的原料。可以长，可以细。

### 2.1 必须包含的六节

| 节 | 标题 | 内容要求 |
|---|---|---|
| 1 | 这次评测回答了什么 | 三问：它现在好不好 / 改完变好还是变坏 / 坏在哪一类。用 1.1 的两个数字直接回答 |
| 2 | 方法与变量控制 | 被测对象定义、为什么全文注入、30 个 case 的三类分布、为什么 judge 只答事实不打分、rubric 版本与 sha256 |
| 3 | 结果 | 开卷 30/30 vs 闭卷 23/30；四维度均分对比；失败分布表 |
| 4 | **归因** | 1.3 那张三组表 + "4 条漏检却通过"。**这一节是报告的心脏** |
| 5 | **rubric 自身的演化** | 1.4 的三个案例 + "3/4 的洞在适用范围"这个结论 + "人肉试评一个没发现" |
| 6 | 结论与下一步 | 该改什么（按优先级）+ 哪些是已知局限（样本 30 条、单被测对象、judge 与被测同厂商） |

### 2.2 三条硬性口径（违反即返工）

1. **作废轮次不得进入任何统计数字**，只能作为"可追溯性实践"的例子出现。
2. **每个结论必须能指到具体 case ID**（如 C006、C019、C026、C029）。写不出 case ID 的结论就是空话，删掉。
3. **不许写"通过率有待提升"这类提分式表述**。评测的目的是定位问题，不是提分。要写的是"失败集中在哪、为什么、下一步改什么"。

### 2.3 验收标准

- [ ] 数字与 1.1 / 1.3 完全一致（对不上的以 `judged/summary.json` 为准，并回报差异）
- [ ] 第 4、5 节里每条结论都带 case ID 或 rubric 版本号
- [ ] 全篇没有"优化""提升""改进效果显著"这类无主语的词
- [ ] 一个没读过项目的人（比如面试官）读完第 1 节和第 6 节，能复述出"它发现了什么"

## 3. 交付物 B：对外展示页（这就是"界面"）

**输出**：单文件 `reports/showcase/index.html`（无外部依赖，双击可开，也可发布成在线链接）
**定位**：面试官 60 秒看懂。不是 Web 应用，不要登录、不要后端、不要交互逻辑。

### 3.1 一屏 6 格，从上到下

1. **顶部横幅一句话**：`同一批 30 道题、同一套评分标准，只改"给模型看多少材料"——通过率从 100% 掉到 76.7%，失败 100% 归因到检索。`
2. **三个数字卡**：开卷通过 30/30 · 闭卷通过 23/30 · 失败 7 个（全部 B 型漏检，零编造）
3. **归因三组条**：检索命中 0/11 失败 · 检索漏检 7/11 失败 · 应拒答 0/8 失败
4. **维度对比图**：四维度开卷 vs 闭卷（用纯 CSS 条形即可，不要引图表库）
5. **失败类型分布**：7 个全是 B 型漏检，0 个 A 型编造
6. **rubric 演化时间线**：v1.1 → v1.4 四个版本，标注"3/4 的漏洞在适用范围"，附 C026、C029 两个案例各一行
7. **底部**：飞书看板截图 1 张 + 一句"判定引擎不只是省人力，它是标准本身的质检器"

### 3.2 技术要求（写死，别发挥）

- 单个 HTML 文件，样式内联，**不引 CDN、不引图表库**（保证离线可开）
- 浅色背景、深色文字，A4 竖版观感，宽度上限 1000px 居中
- 图表用 CSS 条形/纯 SVG 手绘，不用 Chart.js
- 每个图表下方配**一句结论文字**（图表自己不会说话，这句才是给面试官看的）
- 截图区留 `<img>` 占位，路径指向 `screenshot.png`，图由人工补

### 3.3 验收标准

- [ ] 断网双击能正常打开，无报错、无缺图
- [ ] 从上到下读完不超过 60 秒
- [ ] 遮住所有图表只看结论文字，仍能看懂这个项目发现了什么
- [ ] 不含任何"登录""点击查看详情"等需要交互才能看到的信息
