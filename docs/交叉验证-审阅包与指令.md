# 交叉验证：审阅包与指令

日期：2026-09-12  
对应：`docs/执行方案.md` 节点 4 第 2 条  
产出目标：`reports/交叉验证-R001-<日期>.md`（一页）

---

## 一、为什么必须换一个 Agent

不是流程规定，是已经验证过的现象：

> **R001 上线前，人肉试评了 3 条，4 个洞一个都没发现；质检引擎第一次全量跑，一次撞出 3 个。**

原因：**写标准的人知道它「想说什么」，陌生读者只知道它「写了什么」。**  
所以审阅者必须是**没参与过这个项目、没读过这版标准**的人。

**排除清单**

| 候选              | 出局原因               |
| --------------- | ------------------ |
| 施工会话            | 标准是它写的             |
| 豆包工作            | 报告是它写的（等于自己审自己）    |
| 老师会话（WorkBuddy） | 这份标准已被讨论数天，视角已污染   |
| 任何带着项目背景读标准的读者  | 会不自觉地替标准补上它没写清楚的部分 |

→ **选一个跟项目无关的模型，开一个全新会话，只喂材料、不喂背景。**

## 二、审阅包

### 给它的

1. `rubrics/评分标准.md` 全文（R001 v1.4）
2. `reports/评测报告-R001-20260910.md` 全文
3. （可选）3–5 条代表性 case，建议选：
   - `cases/C019.md` —— 测「会不会编」
   - `cases/C022.md` —— 测「提到过 vs 讲过」
   - `cases/C026.md` —— 提示注入（安全类拒绝）
   - `cases/C029.md` —— 要求输出整份文档（正确拒绝却被格式维扣分那一条）

### 不给它的

- 项目背景、开发过程、任何内部讨论
- 任何「我们希望它发现什么」的暗示
- `rubrics/修改记录.md`（内部视角，会带偏）

**理由：不给背景，才测得出这份标准自不自治。** 如果一份标准只能被知道内情的人读懂，它在真实团队里就是不可用的——这本身就是一条结论。

## 三、审阅指令（照抄发给它）

```
你是一位独立的评测标准审阅者，没有参与过这份材料的任何环节。

我会给你两样东西：一份 LLM 输出评测的评分标准，和一份用这套标准写出来的评测报告。

你的任务不是打分，是挑毛病。请只回答下面四类问题：

1. 【歧义】这份标准里，哪一条档位描述可以被读成两种意思？
   逐条抄出原文，并写出两种读法分别是什么。

2. 【适用范围】有没有哪一维被用在了不适用它的题上？
   请重点看「拒绝是否恰当」这一维——标准里写它只对 edge / adversarial 适用。
   有没有哪一类 case 在这一点上是模糊的？

3. 【缺口】有没有明显应该评、但标准里完全没有的方面？

4. 【跳跃】报告里的结论到证据之间，有没有逻辑跳跃？指到具体章节。

硬性要求：
- 每条必须指出具体的原文位置（哪一维、哪一档、或报告哪一节）。
- 不要提「建议扩大样本量」「建议引入人工复核」「建议补充更多 case」这类通用建议
  ——它们对任何评测都成立，等于没说。
- 宁可少提，不要凑数。提 2 条真问题，好过 10 条套话。
- 如果你认为某一部分没问题，直接说「这一部分我没找到问题」，不要硬找。
```

---

## 四、它交回来之后：记录格式

必须逐条表态，**不认同的也要写理由**。

| # | 它提了什么 | 原文位置 | 我认同吗          | 理由 / 下一步                  |
| - | ----- | ---- | ------------- | ------------------------- |
| 1 |       |      | 认同 / 不认同 / 待定 | 改 rubric / 排进 P 列表 / 记为局限 |
| 2 |       |      |               |                           |

---

## 五、验收三条（不满足即返工）

1. **每条意见逐条表态 + 理由**，不许只做摘要。
2. **至少一条是具体的**——能指到 rubric 的某一行或报告的某一节。拒绝「建议扩大样本量」这类万能话。
3. **认同的意见要写下一步怎么处理**：改 rubric / 排进 P 列表 / 记为已知局限。

---

## 六、做完这件事意味着什么

- `docs/执行方案.md` 的五个节点全部有产出，主线交付完成。
- 之后的检索回归、judge 换厂商、仓库转公开，全部属于**加分题**，不再是欠账。
- 如果它又撞出一个 rubric 的洞，那就是第 5 个洞——直接进复盘长文。

## 七、怎么发（操作纪律）

### 发什么

**只发一份文件：`docs/交叉验证-发给审阅Agent.md`**（自包含：审阅指令 + rubric 全文 + 报告全文 + 4 条 case）。

**本文件（你正在读的这份）不要发出去。** 它的第一、四、五节都是给内部人看的——第一节说明"我们在防什么"（等于给暗示），第四节是**你事后填表态**的表格（给它会绑架输出形状），第五节是验收标准（它知道就会迎合）。第二章只是**文件清单**，发过去它手上什么都没有。

### 怎么发

1. **新开一个全新会话**，上下文干净。
2. 全选复制那份文件内容 → **整段粘贴** → 直接发送。
3. **一个字都不要加。**

### 为什么不要拆成「指令 + 两个附件」

两个风险，都会造成**假阴性**（它看起来审了，其实没读到全文）：

- 客户端可能对上传文件做**摘要或截断**，它读到的不是全文；
- 附件读取会失败或分次处理，你不知道它到底吃进去了多少。

**粘贴原文没这个问题**——文本就在消息里，它读到什么，你一眼能看出来。

### 绝对不能加的三类话

| 类型 | 例子 | 后果 |
|---|---|---|
| 给背景 | "这是我在做的评测项目，帮我看看" | 它开始替标准补上没写清的部分——正好毁掉要测的东西 |
| 指重点 | "重点看看拒绝那一维" | 指令里已经有这个重点，是设计好的；你再加一句就是明示答案 |
| 表期待 | "希望你能多提几条问题" | 逼它凑数，套话立刻灌进来 |

（打个招呼、说句"麻烦帮我审一下"——稀释作用，不致命，但没必要。能不加就不加。）

### 发出去之后：看第一轮回复的形状

- **正常的**：直接进入四类问题，或者先声明"我理解了，开始审阅"。
- **要警惕的**：它反问"这份材料是什么背景""你希望我关注哪方面""这是什么项目的标准"。

**应对脚本**（照抄）：

> 材料里有全部信息，请按材料中的审阅指令执行。

不要回答背景问题。它反复要背景，本身就说明**这份标准对陌生读者不够自洽**——这本身就是一条结论，记下来。

### 如果粘贴框装不下

先发指令段（到"输出方式"那句为止），再发第二条只放材料，材料前加一句「以下是材料」。**不要**把材料切成附件。
