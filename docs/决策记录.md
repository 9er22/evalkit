# 决策记录

保留决策过程，两个用途：一是自己回头查"当初为什么这么定"，二是给交叉验证的 Agent 看——它能直接攻击这些理由。

## D1｜为什么不做 RuleSync（标注规则助手）

**原方案**：做一个帮团队撰写、检索、检查、同步"规则/标准"的助手，首个场景取数据标注试标规则。

**否决理由（本人提出）**：数据标注是冷门行业，且自动化程度在提高；作品集的场景会替你说话，冷门场景会反向限制机会。另外那段实习只是为了凑经历去的，投入深度有限。

**我的判断：反驳成立。** 我原来选它的理由是"你有亲历痛点"，但漏了更重要的维度——**场景本身是作品集的一部分**。这是我错了。

## D2｜为什么选 EvalKit

**关键认识**：D1 否决的是**场景**，不是**经验**。

"规则写得不清楚、项目中途改标准、导致返工" 这件事的本质是**质量评估**。而评估是当前 AI 领域公认的最大短板：

- GitHub 上 2026 年多个 Agent 生态清单交叉一致地把 "observability and evals" 写成 production agent 的 table stakes
- 前面调研里也确认：eval 设计是面试中最能立刻建立可信度、也是最多人没准备的一件东西

**为什么它不会过时**：只要模型输出有不确定性，就需要评估。这是结构性需求，不是某个行业的风口。

**差异化**：所有人都在做 Agent，几乎没人做 Eval。

## D6｜第一次全量判定的结果不是"100 分"，是"0 区分度"

2026-09-09，R001 v1.4 下跑完 30 条：通过 30/30，事实性均分 3.0（满分），零失败。

**我的判断**：这不是被测模型强，是这套题根本没有区分能力。全文注入 5 万字语料 = 开卷考试，答案就在眼前，rubric 里设计好的失败类型 **B（语料有但没检索到）在物理上不可能发生**——因为压根没有检索环节，只有"看没看见"。

唯一拉开差距的是「拒绝是否恰当」一维（均分 2.2），扣分集中在知识边界类拒答没给替代路径（C019/C020/C021/C024 都是 7/9）。也就是说：**现在这套 case 真正测到的只有"会不会拒绝、拒绝得周不周到"，完全没测到"会不会找错、找漏"。**

**决策（我定的，属于题目与产出标准范围）**：加一个难度层，不改被测对象、不改 30 个 case——

- 同一批 30 个 case 再跑一轮 **闭卷模式**：每个 case 只注入"相关片段 + 干扰片段"（模拟真实 RAG 的检索结果），而不是整份语料。
- 对比两轮差距：开卷 vs 闭卷的通过率差、B 型失败出现几个、哪些 case 只在闭卷下崩。
- 理由：这样才有真实的失败分布可报告，也才对得上"AI 辅助的产品经理"关心的问题（检索错了到底是检索的锅还是模型的锅）。

**不做**：不为了"制造失败"去把 case 改刁钻。case 不动，动的是信息供给条件——这才是真实线上会变的东西。

## D7｜不用行将过期的内测模型做主口径（2026-09-09）

**背景**：D6 定下的闭卷第二轮，初版是用 V4.1-flash-beta 跑的（模型名 `deepseek-v4.1-flash-expires-on-0910`）。当时认为"能用最强的就用最强的"。

**纠正**：这是我的判断失误。两个理由——

1. **可复现性**：该模型名次日失效，用它产出的所有数字第二天起谁都复现不了。这跟 rubric 里「标准版本可追溯」是同一个道理，我却在自己的实验口径上犯了同样的错。
2. **污染归因**：开卷旧轮是 v4-flash、闭卷新轮是 V4.1，两个变量同时变，结论不成立。第一轮对比白跑。

**决策**：主口径固定为公开的 `deepseek-v4-flash`。`.env` 的 `DEEPSEEK_MODEL` 已改，注释里写清作废的两轮。

- 作废：`runs/20260909-143435`（闭卷）、`runs/20260909-143859`（开卷对比）
- 有效：开卷 `runs/20260908-202726` + 闭卷 `runs/20260909-173030`，同为 v4-flash
- 飞书质检表：QC-T004 标作废（留痕不删），新增 QC-T004-v2 承载修正后的 76.7%

**顺带的一个技术坑**：`/models` 接口**不返回内测模型名**，不能用来判断某个模型是否还可用——我据此误判过一次"V4.1 已下架"，实际发一次请求才知道它还在。

**一个免费收获**：同一套题，V4.1 闭卷 25/30 vs v4-flash 闭卷 23/30。模型能力差异是有的，但远小于信息供给方式带来的差距（−7 条）。**所以遇到问题先查信息供给，别急着换模型。**

## D8｜放弃把火山方舟 Coding Plan 接进评测（2026-09-10）

**起因**：常硕买了火山方舟 Coding Plan 个人版（订阅制，一个月有效，含 deepseek-v4-flash / kimi-k3 / glm-5.3-flash 等），想用它替换 DeepSeek 官方 key 来跑评测，把订阅额度用掉。

**我先把代码接好了**（`PROVIDERS` 供应商层，见 `src/run_eval.py`），然后去查官方条款，结论是**不能用**：

> 火山方舟《套餐概览》：套餐额度仅在 AI 编程工具中生效，**不可用于 API 调用**。在非 AI 编程工具中使用方舟 Coding Plan 权益对应的 Base URL 和 API Key **有可能被识别为滥用/违规，会导致订阅停用或账号封禁**。

EvalKit 的 runner 是 Python 脚本直连 API，不属于「AI 编程工具」。拿封号风险换几十块额度不划算——尤其这是要放进作品集的项目。

**决策**：

1. **默认供应商设为 `deepseek`**（不是省钱的 ark）。要用火山必须显式 `--provider ark`，责任在使用者明确指令。
2. **降级方向单向**：ark 出故障（4028 额度耗尽 / 401 / 429）会退回 DeepSeek 官方；**官方出问题时不会自动倒进 ark**——不能把流量往违规方向引。
3. 模型解析顺序修正：官方注册表补了 `deepseek-v4-flash` 等完整名的自映射。否则写完整名又不指定供应商时会被解析到火山去（两家模型名撞车），等于默认踩红线。
4. 额度留给它该去的地方：**TRAE / Claude Code / Cursor / Cline 这类 AI 编程工具**，做开发时消耗。

**成本对比**（供以后判断值不值）：开卷一轮 30 case ≈ 39.6 万输入 token。按 DeepSeek 官方价，一轮也就几毛到几块钱量级。

**方法论**：这次和 D7 是同一类错误的两面——D7 是"口径不可复现"，D8 是"贪便宜踩合规线"。**接第三方资源前先读它的条款，而不是先写代码。** 好在这次的顺序是先读完条款再定默认值，没有把违规路径做成默认。

## D9｜作废轮次要机器可检查；judge 的维度分会抖、结论不抖（2026-09-10）

三件事，都是写完评测报告后回头收拾的。

### 1. 作废轮次不能只靠人记

`runs/` 下躺着 13 个不能进统计的轮次：两个只跑了 C001 没跑完（`20260910-195358`、`20260910-205028`）、一堆 1 条的冒烟轮、一个跑 20 条中断的、几个用废弃/已过期模型跑的。之前只靠文档写"哪些有效"，但 `qc_engine` 的"取最新一轮"默认行为会直接选中最新目录——**哪天新跑一个 1 条的冒烟轮，下次判定就会默认判它**。

做法：**不删数据，在轮次目录里放 `作废.md`（写明状态与原因），并生成 `runs/轮次台账.md` 汇总。** `qc_engine.py` 跳过任何含 `作废.md` 的轮次（含默认选轮），要强行操作得加 `--force`。登记入口统一在 `src/mark_void_runs.py` 的 `PLAN`。

理由和 D7 一致：删掉即销毁证据，别人无法复核"为什么它不算"。留痕 + 明确排除，才叫干净排除。

### 2. 拒绝维的计分范围：标准写了，引擎没执行

R001 v1.4 第 6 条写明「拒绝是否恰当」仅 edge / adversarial 计分，但 `qc_engine.py` 的维度均分把 30 条全算了进去，18 条 normal 本不该计的分混进均分。

修正：`dim_avg()` 按标准只对 edge/adversarial 统计拒绝维；新增 `--recompute`，**用已有 `judged/*.json` 离线重算 summary，不重跑、不重新调用 judge**。两轮重算结果：

| 拒绝是否恰当 | 修正前（30 条） | 修正后（12 条） |
|---|---|---|
| 开卷 | 2.27 | **2.33** |
| 闭卷 | 1.93 | **2.17** |
| 差 | −0.34 | **−0.17** |

修正后差值更小，**反而更支持主结论**：拒绝能力几乎不受信息供给影响。这是第 5 处"适用范围"类问题，性质与 rubric 那 4 处不同——不是标准有洞，是标准与实现不一致，而且是在报告复核数字时发现的。这正好是「标准版本可追溯」该抓的东西。

### 3. judge 稳定性：结论稳，分数不都稳

重判 5 条（C001、C010、C013、C016、C025）：**3 条维度分变了 ±1**（C001/C010/C013 的「表述与可落地」1→2；C016 拒绝维 2→3），但**通过/失败结论 5/5 与原始判定一致**。

所以：通过率是稳的，可用；维度均分有 ±0.03 量级抖动，**不要拿小数点后第二位做结论**。这也印证了 `rubrics/修改记录.md` 里的遗留项——「表述与可落地」的 2/3 分界还没写成硬行为锚点。

注意：v1.3 那次"两次判定完全一致"的验证只测了 C019、C026 两条，都落在稳定档，所以结论下早了。**稳定性结论要按维度分开下，不能一句"判定可复现"概括。**

## D10｜一份数据只允许一个源：报告 / 展示页 / 飞书都是 summary.json 的投影（2026-09-12）

### 起因：一天之内撞了两次同一个病

2026-09-12 做留痕补齐时发现，同一组数字被抄进了三处，而抄的时候口径不一致，事后没人知道哪份是对的：

1. **展示页**用的是 D9 重算前的 `2.27 / 1.93`（报告已是 `2.33 / 2.17`）。连带那句结论"拒绝维降得最多"也失真——**修正后它是四维里降得最少的**。
2. **飞书判定明细**停在重算前的口径：`normal` 类别的记录还挂着「拒绝是否恰当」的分。飞书图表是**实时 rollup**，这一列只要带分，均值就一定算成旧值。
3. 更值得一提的时间线：**报告 9/10 22:24 出、展示页 9/10 22:26 出**，D9 当夜只改了报告、没回头同步展示页。**同一天里隔两分钟的东西都会漏**——说明"靠人记"这条路根本不通。

三次的根因是同一个：**数字不是算出来的，是抄出来的。**

### 决定

**同一份数据只允许一个源**——`runs/<轮次>/judged/summary.json`（单条明细以 `judged/C*.json` 为准）。报告、展示页、飞书表与看板**全部是它的投影（projection）**，不允许手改、不允许各算一遍。

### 同日落地的配套

- **`src/sync_runs.py` 改成可重跑**：新增 `resync_verdicts()`，对已存在记录做 diff 后 `batch_update`。此前 `batch_create` 只跳过已存在的键、**不更新**——所以 `qc_engine --recompute` 之后重跑 sync 是个**空操作**，飞书会一直停在旧口径（这正是第 2 条问题的机制）。本次已重同步 120 条。
- **飞书维度列只写"适用"的分**：拒绝维仅 `edge / adversarial` 写分，其余写 `null`。原因同上——飞书图表没法按类别过滤，不写 null 均值必然算错。投影口径与 `qc_engine` 的 `REFUSE_DIM_CATEGORIES` 对齐，改一边必须同步另一边。
