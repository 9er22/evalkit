# 决策记录

保留决策过程，两个用途：一是自己回头查"当初为什么这么定"，二是给交叉验证的 Agent 看——它能直接攻击这些理由。

## D1｜为什么不做 RuleSync（标注规则助手）

**原方案**：做一个帮团队撰写、检索、检查、同步"规则/标准"的助手，首个场景取数据标注试标规则。

**否决理由（本人提出）**：数据标注是冷门行业，且自动化程度在提高；作品集的场景会替你说话，冷门场景会反向限制机会。另外那段实习只是为了凑经历去的，投入深度有限。

**我的判断：反驳成立。** 我原来选它的理由是"你有亲历痛点"，但漏了更重要的维度——**场景本身是作品集的一部分**。这是我错了。

## D2｜为什么选 EvalKit

**关键认识**：D1 否决的是**场景**，不是**经验**。

"规则写得不清楚、项目中途改标准、导致返工" 这件事的本质是**质量评估**。而评估是当前 AI 领域公认的最大短板：

- GitHub 上 2026 年多个 Agent 生态清单交叉一致地把 "observability and evals" 写成 production agent 的 table stakes
- 前面调研里也确认：eval 设计是面试中最能立刻建立可信度、也是最多人没准备的一件东西

**为什么它不会过时**：只要模型输出有不确定性，就需要评估。这是结构性需求，不是某个行业的风口。

**差异化**：所有人都在做 Agent，几乎没人做 Eval。

## D3｜经验怎么放（位置问题）

- ✅ 放进 `research/亲历_标准不一致.md`——作为**动机**和**一手判断力**的来源
- ❌ 不放进产品场景——不把项目绑定在任何具体行业上
- 语料与被测对象一律用**公开通用材料**，避免作品集被贴行业标签

## D5｜那段亲历在项目里的位置（用途边界）

2026-09-08 本人明确：那次"标准来回改"的经历**不重要，不需要继续深挖复盘**。

**它是指导，不是素材。** 本人定的三条意义：

1. 验证「质量保证与流程交付」的价值，以及 QA + PM 岗位职责的一体性；
2. 结合 AI 的方向去探讨其意义；
3. 思考我们的项目该怎么避免这类事情在工作中发生，降低它发生的概率。

**由此产生的硬约束**：

- `research/亲历_标准不一致.md` 只写到"能推导出 rubric 维度"为止，**不再展开返工细节的复盘**；Q2、Q3 如实写"记不清"，不编。
- README 里"我为什么做这个项目"**等节点 4 报告出来后再写**。提前写只能写出空话。
- 这段经历的产出是**一个 rubric 维度**（标准版本可追溯），不是一个功能模块。不为了它加功能。

**我的判断**：第 3 条是本条里最狠的一句——它要求 EvalKit 自己不能犯同样的毛病。所以「版本可追溯」必须是 rubric 的内置维度，不能是事后补的文档。
